    左边线突出本事件改动的节点。 三种事实要分开看：本地提交、投递状态、生成结果。

      这是源码分支的事件模型，不运行数据库或 RabbitMQ。正常路径选择“先标 sent，再消费”的一种合法时序；实际消费可与 relay 交叠。图中的消息到达是单独观察事件，不能从 Publish 的 nil 返回推导出来。

      判断可靠性，按这三个问题走

      1. 本地提交了吗？ chart 和 outbox 都用同一个 tx。任一次写入失败就回滚；提交成功留下 wait + pending，表示受理了工作及其投递意图，不表示结果已生成。
      2. 投递在哪个边界停下？ 返回错误时保留 pending，正常的计数更新使 retryCount + 1；后续仍可扫描。Publish 返回 nil 后，标 sent 之前仍是 pending；若此时崩溃，下一轮不知道上次是否已经发出，只能再发 101。
      3. 领取资格等于完成结果吗？ CAS 只允许 wait → running。重复消息命中 0 行会跳过；它没有证明 succeed，更没有把 running 的失联执行者恢复起来。

      事务绑定的是两次本地写入，不是一次端到端执行。sent ≠ succeed；CAS 跳过 ≠ 完成恢复。

      当前实现不能承诺全链路不丢不重

      生产者设置了 DeliveryMode: Persistent，但没有启用 publisher confirms，且 mandatory=false，没有不可路由消息的退回处理。Publish 返回 nil 只是客户端返回成功，不是 broker 已持久化或已成功路由的证据。 relay 随后就会标 sent，因此不能宣称“保证无损”或 exactly-once。

      源码能支持的结论是：受理时持久化投递意图，返回错误后保留可重试记录，允许重复投递，并用状态 CAS 限制重复启动。重复消费去重和执行完成恢复仍是不同问题。

      看完正常路径，再在上方依次改变 outbox 写入、Publish 返回值和崩溃位置。沿同一图表看哪一层变了，其他层为什么没变；最后用消费者崩溃分支检查“跳过”并不等于“完成”。

      按需查阅：源码、术语和适用边界

      源码基线：6a0384cbf3a1f1901d5f7e5401fc5905d7590a49；分析日期：2026-11-08。已比对下列关键文件与基线一致；行号只作辅助定位。

      • ChartService.SaveWait：两次 tx.Create 在同一个 db.Transaction 中；outbox 用 chart.ID 作为 aggregateId 和字符串 payload，错误时返回业务失败，不交付成功受理 ID。
      • relay 的数据库操作：只扫描 pending；markSent 更新 sent；incrementRetry 只增加计数。runOnce：先 Publish，再标 sent；Publish 报错就计数并继续，标 sent 失败也会留下 pending。retryCount 不是自动丢弃阈值。
      • Producer.Publish：调用 PublishWithContext，mandatory 为 false，设置 Persistent。MQ 信道初始化没有启用 confirms；不能把“持久化标志”当成“已经确认落盘”。
      • ProcessChart 与 CAS 结果分类：status = wait 才更新 running，0 行返回 ErrAlreadyProcessed；调用 AI 后另一次更新 succeed、genChart 和 genResult。
      • Consumer.handle：CAS 哨兵错误走直接 ACK 分支，不重试、不 MarkFailed、不发状态事件。正常生成完成后才发布 succeed 事件并 ACK。ACK 是消费端确认，不是 publisher confirm。

      模型的假设与省略

      图表 ID 101 是教学实例；outbox 的自增主键不必等于 101，图上“101 的消息”指 aggregateId / payload。失败事务不保证回收已经分配的自增 ID。

      演示假定 SQL 提交、retryCount 更新和标 sent（未注入故障的步骤）成功，扫描与消费者最终有机会运行，收到消息后按所选时序处理。Publish 错误分支假定那一次没有到达；真实错误也不能证明远端一定没收到。

      relay 崩溃分支只改变投递进程：首次 Publish 返回 nil 后、标 sent 前退出，再启动会立即扫描。消费者崩溃分支则假定连接中断后，尚未 ACK 的原消息被重新投递；它不是第二次 Publish。该分支没有走正常错误返回或重试耗尽兜底，因此 chart 仍是 running。

      页面没有模拟多 relay 实例并发扫描、MQ 重连、数据库扫描错误、消费超时或死信。当前 relay 没有领取租约，消费者 CAS 也不是失联任务的回收机制。源码注释中的“不丢”及“exactly-once 效果”应按上述实际确认边界收窄。

      若增强确认、退回处理、重连或执行恢复，需要另加机制；本页不把这些未实现方案画成既有行为。更多链路见完整课程 C04。
