    本次已发生的因果链：

      再改变一个条件：这条健康连接如果后来真的断开，才会触发另一条刷新路径。断开不会补发旧通知。

      主链看懂后：只交换“完成”与“订阅”的顺序
      保持图表 101、查询结果和网络条件不变；切换后从 T0 重新走

      此处“完成”合并展示成功写库及随后发布通知，不代表二者是一个原子事务。默认通知发布、可接收时的转发与列表请求都成功。

      这是简化模型，不是真实网络测试。固定当前页、仅一张图表；窗口内轮询计时器尚未触发，也没有已发出的查询、用户刷新或其他通知。每次点击推进一个观察步骤，T 编号不是耗时。实际服务端先 flush 响应头再调用 Subscribe；“订阅生效 + open”在本图合为一步，正常分支额外假定订阅确已生效，浏览器 onopen 本身并不确认 Redis 订阅。

      判断收敛，只问三件事

      1. 事实已经变了吗？消费者成功写 succeed 后，数据库有结果；但页面仍持有上一次列表快照，不会自动共享这次写入。
      2. 谁会触发下一次查列表？订阅及时且通知到达，事件回调发起查询；漏过通知而连接一直 open 时，当前实现又关了轮询，未必还有自动查询入口。15 秒注释心跳不触发 onmessage。
      3. 查询响应被接受了吗？成功返回并更新当前列表，页面才显示 succeed。断连只是把 fallback 设为 true；等轮询查询返回才收敛，不能把 onerror 当成拿到结果。

      不变量：页面状态来自列表响应，不来自连接状态。通知漏过后，数据库 succeed + SSE open + 轮询关闭，仍可能得到页面 running。

      同样的图表 101，只把完成时刻移到订阅之前，就能解释为什么“已连接”不保证进度；再触发断连，则能看到轮询如何绕过丢失通知、直接读取持久状态。

      术语只保留这里需要的区别

      Redis Pub/Sub 是当前订阅者接收的消息通道，后订阅不会回放过去消息；本项目的 SSE 包装也未增加事件存储、事件 ID 或 Last-Event-ID 补发。pending 指页面列表中的 wait/running；即使 DB 已 succeed，旧列表仍使 pending=true。收敛 指页面成功接受新列表响应后，与数据库终态一致。

      模型边界

      主链拆开“发布”“到达”“查询返回”，让通知与状态更新分别可见；实际它们可能很快连续发生。关闭连接、清理订阅也压缩到观察步骤。failed 的刷新路径类似，但本示例只演示成功写库，不推断失败写库一定成功。

      单图表模型不覆盖多个连接共享 fallback 布尔值、搜索分页的响应竞态、可见性变化与旧请求返回后再调度。已有请求仍可能在关闭轮询后返回；所以本图的停滞是明确条件下的可能结果，不是每次都会发生。

      未来方案，不是当前实现

      可以考虑在健康 SSE 下仍保留低频状态对账，或订阅确认后补发当前状态；处理并发快照与通知时还需版本约束。这些增强尚未实现，本页没有把它们模拟成现有兜底。当前可见的轮询兜底来自断连、建连超时或 EventSource 不可用，不来自“通知已经漏掉”的检测。
