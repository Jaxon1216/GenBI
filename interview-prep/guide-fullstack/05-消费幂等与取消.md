# C05 消费者领取任务：幂等、超时与重试边界

> 课程性质：核心  
> 返回：[主导学](../GenBI/导学.md)；前置：[C04 事务消息表](04-事务消息表.md)；下一课：[C06 SSE 与轮询](06-SSE与轮询.md)。  
> 对应：B3；[Q3 消费与超时](../GenBI/面经.md#q3-并发消费与超时)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

图表 101 被重复投递，两条消息可能分别由两个 consumer 收到。数据库条件更新决定谁能从 wait 进入 running，只有抢到的执行者调用 AI。任务状态承担协调作用，但当前状态机把失败后的再次执行也挡住了，必须区分“重复启动被抑制”和“失败任务能恢复”。

默认任务 Context 为 30 秒，覆盖同一消息的整个重试循环；HTTP client 60 秒是另一层兜底。应用循环最多调用两次，不等于 AI 一定重试两次。

## 主链与职责

```text
RabbitMQ delivery → 解析 chartId → WithTimeout(默认30秒)
 → ProcessChart：查 chart → UPDATE ... WHERE status='wait' → running
 → AnalyzeCsv(ctx) → 清洗 → 写 succeed → 发布通知 → Ack

CAS 0行 → ErrAlreadyProcessed → 直接 Ack，不发事件
其他错误 → 等2秒 → 第二次 ProcessChart
仍失败 → MarkFailed → failed事件 → Nack(requeue=false) → 死信路由
```

consumer 采用 prefetch=1、手动 Ack、单个进程串行遍历 deliveries，避免一个消费者提前持有大量未确认任务。多消费者可以并行处理不同任务，共同用数据库 CAS 仲裁同一任务。

决定幂等的真实片段：

```go
res := s.db.Model(&model.Chart{}).
    Where("id = ? AND status = ?", chartID, model.ChartStatusWait).
    Update("status", model.ChartStatusRunning)
if err := classifyCASResult(res.Error, res.RowsAffected); err != nil {
    return err
}
```

两个执行者即使都先读到 wait，也只有一个条件更新能命中一行。关键是把状态条件放进写操作，而不是只在 Go 中先判断状态。

## 机制与边界

正常重复消息场景：A 抢占成功；B CAS 0 行直接 Ack；A 最后写 succeed。这里能确认同一 wait 状态只有一个执行者启动生成。

**当前重试冲突**：A 置 running 后模型失败。两秒后第二次 ProcessChart 仍要求 wait，CAS 0 行，于是返回 ErrAlreadyProcessed，consumer 直接 Ack。任务可能永久 running，不会进入 MarkFailed、failed 事件或死信。即使首次模型已经超时，这条路径仍成立。不能声称失败任务已自动重试并最终收敛。

若失败发生在抢占前，第二次仍可尝试；但 Context 不会重新创建，剩余预算只会更少。数据库读取/更新未普遍使用 WithContext，重试的 time.Sleep 也不响应取消，因此 30 秒预算主要控制传入模型 HTTP 的部分，并非整个处理函数严格墙钟上限。

抢占 running 后进程崩溃，未确认消息会在 broker 允许的条件下重投，但当前 CAS 将其视为已处理，没有租约到期恢复。成功写库后 Ack 失败的重复消息会被跳过，这是合理的抑重路径；这两种 running/succeed 情况不能混为一谈。

死信仅覆盖真正进入 onExhausted 的路径；格式坏消息直接 Ack 丢弃。死信重放也没有自动工具，failed 状态不能直接被当前 CAS 重新领取。成功写结果与 MarkFailed 没有执行版本条件，写库错误的观测也不完整。

## 需要懂什么

幂等要求重复请求不会重复产生副作用；可恢复要求未完成执行能够继续或进入终态。单个 wait→running 门闩保护前者的启动部分，却会挡住后者。正确状态机应区分“别人的活跃执行”“自己的重试”“执行已完成”“租约已过期”。

演进可采用执行令牌与租约，终态写入时检查令牌，过期后有条件重新领取；或者在一次领取之后把模型有限重试放入同一个拥有者的处理阶段。为失败任务建立受控重置/重放策略后，死信才形成恢复闭环。这些均是建议，当前未实现。

Context 是取消信号，不能代替业务恢复。它能让 Go 停止等待 HTTP，但不能撤销已提交数据库状态，也不能证明模型服务器停止计费。

## 需要记住什么

- prefetch=1、手动 Ack；wait→running 条件更新仲裁并发。
- 一个消息共用 30 秒 Context，最多两次 ProcessChart，间隔 2 秒；模型 client 60 秒兜底。
- running 后失败重试可能被 CAS 跳过并 Ack，当前没有租约恢复。
- 死信是保留入口，不是自动恢复；不要口播“不丢不重、失败一定终态”。回到[Q3](../GenBI/面经.md#q3-并发消费与超时)说明两种保证。
