# C04 受理任务与事务消息表

> 课程性质：核心  
> 返回：[主导学](../GenBI/导学.md)；前置：[C03 上传与生成](03-上传与同步生成.md)；下一课：[C05 消费与取消](05-消费幂等与取消.md)。  
> 对应：B2；[Q2 事务消息表](../GenBI/面经.md#q2-事务消息表)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

用户异步上传一份“日期、访问量”表格，HTTP 接口返回图表 ID。这个 ID 表示数据库已经保存任务和投递意图，图表结果要等后台消费者生成。关键结论是：本地事务绑定两张表；relay 负责扫描投递；投递成功后标记 sent 仍存在重复窗口。数据库原子提交的范围不包括 RabbitMQ。

## 主链与职责

```text
AddChartAsync → multipart /chart/gen/async → 参数解析、限流
             → SaveWait：同一 MySQL 事务写 chart(wait) + outbox(pending)
             → HTTP 返回 chartId → 页面跳转“我的图表”
server 内 relay → 扫 pending → Publish(chartId) → 成功标 sent
                                              → 失败保留 pending，retryCount + 1
RabbitMQ → 独立 consumer → 查询 chart，生成并写入结果
```

chart 保存业务输入和执行状态；outbox 保存投递状态和仅含图表 ID 的消息载荷。两套状态分别回答“生成到哪一步”和“是否已尝试完成投递”。sent 不表示图表 succeed。

## 源码阅读

1. [异步页面](../../frontend/src/pages/AddChartAsync/index.tsx)的 `onFinish`：拿到非空 `res.data` 就提示提交成功，随后跳转；没有在此等待结果。
2. [ChartHandler](../../backend/internal/handler/chart_handler.go)的 `GenAsync`：先解析上传内容，检查 producer 非 nil，再限流；调用 `SaveWait`，没有直接 Publish。
3. [ChartService](../../backend/internal/service/chart_service.go)的 `SaveWait`：`tx.Create(chart)` 后用回填主键构造 outbox，两次 Create 都使用 tx，任何错误都交由 Transaction 回滚。
4. [Outbox 模型](../../backend/internal/model/outbox.go)和[建表 SQL](../../backend/sql/02_outbox.sql)：payload 是 ID 字符串，status 有 pending/sent，索引在 status 上。
5. [relay](../../backend/internal/outbox/relay.go)的 `Start`、`runOnce`：启动立即扫一次，之后默认每 5 秒扫最多 100 条；按 id 升序逐条处理，单条失败继续下一条。
6. [生产者](../../backend/internal/mq/producer.go)的 `Publish`，然后接[C05](05-消费幂等与取消.md)：消息持久化标志设置为 Persistent，消费端再按 ID 抢占业务任务。

关键片段来自 `SaveWait`：

```go
err := s.db.Transaction(func(tx *gorm.DB) error {
    if err := tx.Create(chart).Error; err != nil {
        return err
    }
    msg := &model.Outbox{
        AggregateID: chart.ID,
        Payload: strconv.FormatInt(chart.ID, 10),
        Status: model.OutboxStatusPending,
    }
    return tx.Create(msg).Error
})
```

若第二次写入失败，第一次也回滚。HTTP 不会交付一个仅落下 chart 的成功受理结果。这是在当前数据库内消除双写间隙的原因。

## 机制与边界

假设图表 101 提交成功，outbox 记录还是 pending。下一轮 Publish 报错时，relay 增加 retryCount，保持 pending，后续继续扫描；它不按次数自动丢弃。这使短暂投递错误留下可补发记录。

若 Publish 返回成功、但标记 sent 前进程退出，重启后的 relay 会再次发 101。多 server 实例也没有扫描租约或行抢占，可能同时读到同一条记录。重复投递由消费端状态 CAS 限制重复启动，但它没有解决执行中崩溃的恢复，详见 C05。

**必须缩小保证范围。** 生产者未启用 publisher confirms，`mandatory=false`，没有处理不可路由退回；Publish 返回 nil 不能作为 broker 已可靠落盘、成功路由的最终证明。源码注释写“relay 不丢”或“端到端 exactly-once 效果”时，仍应以这些实际调用为准。当前可以确认“投递意图持久化、返回错误后保留待补发记录”，不能宣称全链路不丢不重。

启动时 MQ 连接失败，会让异步接口拒绝受理。即使 MQ 已连接，配置关闭 relay 仍不会阻止 handler 写入任务，此时 pending 无人扫描。连接建好后也没有自动重连实现。默认 100 条/轮限制的是一次扫描数量，不能当作数据库队列总容量或严格吞吐上限。

## 需要懂什么

事务保证的是两个数据库写入共同提交。把网络 Publish 放进数据库事务，会延长锁占用，并不能让数据库 rollback 撤销已发出的消息；outbox 把跨系统协作改成“本地提交 + 后台推进”。

至少一次投递与幂等执行是两个层面。relay 可以重发；CAS 让 wait 任务仅一个消费者抢占；执行者抢占后挂掉则需要另一种恢复机制。状态中间态既用于协调，也决定重试能否继续，不能简单把“不重入”当作“最终会完成”。

若要增强可靠性，可增加 broker confirms、退回处理、重连，以及带领取租约的 relay；它们属于进阶方案，当前尚未实现。确认后再标 sent 仍可能重复，消费端仍需幂等与恢复。

## 需要记住什么

- 受理成功：chart(wait) 与 outbox(pending) 一起提交；结果成功：消费者写 succeed。
- relay 默认 5 秒、每轮最多 100 条；返回错误就保留 pending 并记录重试次数。
- 发布与标 sent 分两步，存在重复窗口；当前没有 broker 确认、扫描租约或自动重连。
- 按“本地事务 → broker 确认 → 消费抢占 → 执行恢复”顺序说明可靠性。回到[Q2](../GenBI/面经.md#q2-事务消息表)组织口播。
