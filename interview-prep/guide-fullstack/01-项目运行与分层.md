# C01 一次请求进入系统：运行入口与分层

> 课程性质：核心  
> 返回：[主导学](../GenBI/导学.md)；前置：无；下一课：[C02 会话与接口](02-会话与接口契约.md)。  
> 对应：B1；[Q1 分析编排](../GenBI/面经.md#q1-同步与异步分析编排)；目标掌握：看懂链路、理解机制、设计与表达。

## 本课重点

用户在浏览器上传表格，前端负责输入和展示，Go HTTP 服务负责受理与查询，独立消费者负责后台 AI 生成。同步模式在当前请求中等待结果；异步模式先保存任务，消费者随后完成。把两个进程画出来，比把项目背成技术栈清单更有用。

主要状态分成三类：React 的提交与列表状态、MySQL 的业务任务状态、EventSource/定时器等连接资源。它们的生命周期与事实来源各不相同。

## 主链与职责

```text
React/Umi :8000 → 开发代理 /api → Gin server :8080
                                    ├─ handler → service → GORM/MySQL
                                    ├─ Redis：会话、限流、订阅事件
                                    └─ outbox relay → RabbitMQ
独立 consumer → RabbitMQ → ChartService → DeepSeek → MySQL
              └─ Redis Pub/Sub → server SSE → React 再查询
```

handler 处理 HTTP 参数与响应；service 负责业务规则与数据库读写；bootstrap 组装路由、会话与基础设施。依赖在 main 中显式构造，没有 Wire 或运行期 IoC 容器。消费者复用 ChartService 与模型调用服务，因此同步和异步可以共用生成规则。

## 源码阅读

1. [前端依赖](../../frontend/package.json)与[后端依赖](../../backend/go.mod)：React 18、TypeScript 5.9.3、Umi Max 4、Gin、GORM；go.mod 声明 Go 1.25.0，README 的 Go 1.24 描述不能代替清单。
2. [前端路由](../../frontend/config/routes.ts)：上传、异步上传、我的图表、看板是四个主入口。[代理](../../frontend/config/proxy.ts)仅 dev 环境转发 /api 到 8080。
3. [server/main](../../backend/cmd/server/main.go)：加载 config，组装 DB、Redis、会话、service、handler、可选 MQ、relay、SSE，再调用 Gin Run。
4. [NewRouter](../../backend/internal/bootstrap/router.go)：全局 recovery/logger/session；/chart 组执行 Auth 后再进入 handler。
5. [consumer/main](../../backend/cmd/consumer/main.go)：另一个入口，构建 DB、模型服务、MQ、事件发布器，再阻塞消费。
6. [Compose](../../docker-compose.yml)和[Makefile](../../backend/Makefile)：Compose 只启动 MySQL、Redis、RabbitMQ；HTTP 与 consumer 仍由两个命令启动。

server 的具体依赖组装：

```go
deepSeek := service.NewDeepSeekService(cfg.DeepSeekAPIKey, cfg.DeepSeekBaseURL)
chartService := service.NewChartService(db, deepSeek)
limiter := ratelimit.New(rdb)
chartHandler := handler.NewChartHandler(chartService, limiter, producer)
```

对象通过构造函数传入，读 main 就能知道运行期使用哪些实现。relay 使用接口抽象存储与投递能力便于 fake 测试，但 ChartService 对 DeepSeek 仍依赖具体类型，不能据此声称所有依赖都可随意替换。

## 机制与边界

server 的 MySQL、Redis 或会话初始化失败会阻止启动；MQ 失败只告警，producer 为 nil，异步接口报“异步服务未启用”，同步路径仍保留。consumer 的 MQ 失败直接退出；Redis 失败则使用 NoopPublisher，继续生成但没有实时通知。这些依赖强弱由进程职责决定。

HTTP 接口返回不等于后台任务开始。数据库受理、relay 投递、consumer 领取是不同时间点，UI 必须用 wait/running/succeed/failed 展示真实阶段。

当前 main 没有注册进程信号或 HTTP Shutdown。relay 的 Start 虽接受 Context，main 传 Background，没有把终止信号接成统一退出链路。数据库也没有显式配置连接池上限或关闭流程。应把优雅停机、容量配置列为演进，不能因为函数里有 defer 就称整个服务优雅停机已完成。

## 需要懂什么

分层价值在于职责和依赖方向：HTTP 绑定变化集中在 handler，生成与状态协调在 service，进程装配在入口。当前有直接暴露 DB 的方法，也不应把分层夸成严格的领域隔离。

异步进程把长时间生成从 HTTP 请求生命周期移开，但系统仍需队列背压、终态更新和恢复机制。同步主要适合立即拿结果的路径；异步主要改变受理与结果交付方式，源码没有测得“大数据模式一定更快”。

开发代理与生产部署是两件事。构建静态资源后不会携带 Umi 开发服务器的代理，线上需要同源网关或明确跨域、Cookie 与 SSE 转发配置。

## 需要记住什么

- 四个主页面、两个 Go 入口、三种基础设施；Compose 没有包办应用进程。
- handler 管 HTTP，service 管业务，bootstrap/main 管装配；依赖为显式注入。
- MQ 失败影响异步受理，consumer 的 Redis 通知可降级；没有统一优雅停机。
- 回到[Q1](../GenBI/面经.md#q1-同步与异步分析编排)，用“谁受理、谁执行、谁保存结果、谁展示”解释全栈协作。
