# 面经：GenBI · 全栈开发

> 以下为目标简历与学习口播，供掌握后选用。分析范围：当前 GenBI 全栈实现；源码基线 `6a0384cbf3a1f1901d5f7e5401fc5905d7590a49`，分析日期 2026-11-08。

## 项目简介（简历可用）

GenBI 是基于 React/TypeScript 与 Go 的智能数据分析应用，用户上传 CSV/Excel 后，由 DeepSeek 生成 ECharts 图表与分析结论，支持同步生成、异步任务进度展示和多图拖拽看板。后端采用 Gin、GORM、MySQL、Redis 与 RabbitMQ，前端使用 Ant Design Pro、Umi 和 ECharts。

## 简历 bullet

- **同步与异步分析编排：** 复用表格转 CSV、分析目标与模型输入构造；同步路径调用模型、保存图表后返回结果，异步路径先保存任务并返回 ID，由独立消费者生成，前端通过任务状态展示等待、执行与结果。
- **事务消息表：** 在同一 MySQL 事务中写入待生成图表与待投递消息，后台 relay 按批扫描并投递 RabbitMQ；发布返回错误时保留待投递记录并累计重试次数，发布成功后更新投递状态。
- **并发消费与超时控制：** 用数据库条件更新仲裁待生成任务，只有从等待态抢占成功的消费者调用模型，重复消息直接确认；将 Go Context 传入模型 HTTP 请求控制超时与取消，并通过预取数量和手动确认控制任务领取与确认时机。
- **SSE 与轮询协作：** 消费者经 Redis 发布图表终态通知，服务端校验归属后用 SSE 转发，前端收到事件重新查询列表；建连成功后关闭轮询，断连或建连超时启用兜底，轮询按状态快照退避并响应页面可见性变化。
- **图表契约与渲染容错：** 将模型返回的配置字符串集中解析，用 Zod 检查图表结构并过滤函数文本与部分敏感字段；失败时提示原因并尝试回退配置，ECharts 由 React 错误边界承接渲染异常，生成页、图表列表与看板共用同一组件。
- **可组合看板与数据预览：** 按图表 ID 关联多图卡片与栅格布局，支持拖拽、缩放和手动保存本地图表快照及布局；原始 CSV 预览使用 react-window 按可见范围渲染行，限制长表格的 DOM 创建规模。

## 面试问题

### Q1 同步与异步分析编排

- 对应支柱：B1
- 触发依据：“同步路径…返回结果”“异步路径…返回 ID，由独立消费者生成”
- 考查目标：理解端到端职责、接口契约与请求/任务生命周期
- 学习入口：[C01](../guide-fullstack/01-项目运行与分层.md)、[C03](../guide-fullstack/03-上传与同步生成.md)

**面试官问题**：你为什么同时提供同步和异步生成？它们怎样共享规则，前端怎样判断任务完成？

**口播版**：我把两种方式的区别放在受理和结果交付上。同步请求先解析表格、构造模型输入，等待模型返回，保存图表后把配置和结论交给页面；异步请求先保存输入和待生成状态，返回任务 ID，独立消费者稍后执行。两条路径共用 CSV、分析目标与模型调用规则。前端同步页直接展示返回结果，异步页跳到个人列表，按等待、执行中、成功、失败展示。异步返回 ID 只代表受理，不代表已经生成。当前生成客户端仍把异步结果声明成同步结果类型，错误 envelope 也有差异，所以这些边界应统一，类型检查通过不能代替实际联调。

**追问 1**：你说异步让独立消费者执行，它是不是就能处理任意大的表格？

**触发依据**：主回答中的“独立消费者稍后执行”“共用 CSV”

**口播版**：不能。异步改变的是等待方式，当前仍整文件转成 CSV，模型输入也没有行数或 token 预算。限流还在解析之后，所以不能保护文件解析阶段。现在回看，大文件需要请求体限制、流式解析、统计聚合或采样，再按预算调用模型；这些不能作为当前已有能力。

**追问 2**：你说模型返回后保存图表，模型成功是否就一定能显示图？

**触发依据**：主回答中的“保存图表后把配置和结论交给页面”

**口播版**：不一定。模型 API 响应可解析、配置 JSON 合法、ECharts 结构可用是不同条件。后端清洗非法配置会回退空对象，仍可能以成功状态保存；前端再检查 series 等结构并提示异常。要更准确，可在服务端落库前完成结构校验，并把生成成功与图表校验失败分开表达。

### Q2 事务消息表

- 对应支柱：B2
- 触发依据：“同一 MySQL 事务…待生成图表与待投递消息”“发布成功后更新投递状态”
- 考查目标：区分数据库原子提交、投递确认与消费效果
- 学习入口：[C04](../guide-fullstack/04-事务消息表.md)

**面试官问题**：为什么要使用事务消息表？写入和投递各自能保证什么？

**口播版**：我把图表任务和待投递消息放进同一个数据库事务，第二张表写失败时两者都回滚，受理成功时就有可扫描的投递意图。HTTP 不直接依赖那次网络发布来完成双写，后台 relay 读取待投递记录，发布返回错误就保留记录并增加计数，后续再尝试。这个事务只覆盖 MySQL，不包含 RabbitMQ。发布与标记完成分开，发布之后标记失败会重发，所以消费者还要按任务状态抑制重复启动。当前生产者没有 broker confirms 和不可路由处理，我能确认本地意图持久化和显式失败后的补发，不能承诺全链路消息绝不丢失。

**追问 1**：你说发布之后标记失败会重发，为什么不在发布前标记完成？

**触发依据**：主回答中的“发布与标记完成分开…会重发”

**口播版**：先标完成再发，如果进程在发消息前退出，下一轮就不会扫描到它，形成永久漏投。先发后标选择接受重复窗口，但还需要 broker 确认和幂等消费。即使增加确认，收到确认后、数据库标记前退出仍会重发，所以确认不能消除全部重复。

**追问 2**：既然有幂等消费，能不能说已经做到 exactly-once？

**触发依据**：上一回答中的“接受重复窗口…幂等消费”

**口播版**：不能。当前 CAS 只允许等待态被一个执行者抢占，执行者置为运行中后崩溃，重投消息也会被跳过；它没有证明最终完成。另外发布还缺少强确认。应分别说明本地提交、投递、启动抑重和执行恢复，只有每一层都有依据才能讨论端到端保证。

### Q3 并发消费与超时

- 对应支柱：B3
- 触发依据：“条件更新仲裁待生成任务”“重复消息直接确认”“Context…超时与取消”
- 考查目标：解释并发不变量、错误分类、取消传播与可恢复性
- 学习入口：[C05](../guide-fullstack/05-消费幂等与取消.md)

**面试官问题**：两条重复消息同时到达时，谁执行模型调用？任务超时后又怎样处理？

**口播版**：我用数据库条件更新领取任务，只有状态仍为等待的行才能被改成运行中。两个消费者即使都先读到等待，也只有一个更新能影响一行，另一个把零行结果识别为重复，直接确认消息。获胜者用 Go Context 调用模型 HTTP，请求取消和超时能传到网络层；消费者默认有三十秒任务预算，模型客户端另有六十秒兜底。这里有一个重要限制：当前失败后的第二次处理仍尝试领取等待态，但第一次已经改成运行中，因此会被当成重复并确认，任务可能卡住。启动抑重成立，失败自动恢复尚不完整。

**追问 1**：你刚说重试会被运行中状态挡住，怎样改才能既不重复执行，又能恢复？

**触发依据**：主回答中的“失败后的第二次处理…被当成重复”

**口播版**：我会把领取和执行重试分开。一个执行者领取成功后，可以在自己的执行阶段有限重试模型，而不是再次用等待态领取；如果还要处理进程崩溃，需要执行令牌、租约到期与受控重新领取，终态更新也检查令牌，防止旧执行者覆盖新结果。失败任务的重放应明确状态转换和审批边界。这是演进方案，当前没有这些机制。

**追问 2**：你提到三十秒预算，重试两次是否意味着每次都有三十秒？

**触发依据**：主回答中的“三十秒任务预算”，上一回答中的“有限重试模型”

**口播版**：当前是同一个 Context 覆盖整个消息处理循环，第二次只有剩余时间。两秒退避不会刷新预算，而且数据库调用和 Sleep 没有完整接入 Context，因此不能说整个函数严格在三十秒内结束。Context 控制等待和取消信号，也不会回滚已经提交的运行中状态。

**追问 3**：无法恢复的任务是不是都会进入死信队列？

**触发依据**：主回答中的“失败自动恢复尚不完整”，追问 1 回答中的“失败任务的重放”

**口播版**：当前不是。只有重试真正耗尽并走到失败兜底，才会写失败、发通知、Nack 不重新入队，再经死信路由保留。运行中被误当重复的路径直接 Ack，不会进死信；格式错误的消息也直接 Ack。死信只是保留与排查入口，当前没有自动重放闭环。

### Q4 SSE 与轮询

- 对应支柱：B4
- 触发依据：“收到事件重新查询列表”“建连成功后关闭轮询”“快照退避”
- 考查目标：区分通知与事实源、分析时序窗口、管理浏览器异步状态
- 学习入口：[C06](../guide-fullstack/06-SSE与轮询.md)、[C08](../guide-fullstack/08-列表状态与数据预览.md)

**面试官问题**：为什么同时使用 SSE 和轮询，前端在什么条件下切换？

**口播版**：我让 SSE 负责尽快通知，数据库列表负责完整结果。消费者写成功后通过 Redis 发布终态，服务端校验图表归属，转发给浏览器；浏览器收到事件就静默查询当前页，不直接用通知拼图表。页面初始允许轮询，SSE 打开后关闭它，断连或建连超时再开启。轮询用图表 ID 和状态形成快照，连续不变时延长间隔，有变化恢复三秒，上限三十秒，并响应页面可见性事件。当前切换策略还有缺口：连接打开并不代表此前的完成事件送达，所以完整收敛仍需要初始状态补齐或周期对账。

**追问 1**：你说连接打开也可能没有完成事件，能举一个具体时序吗？

**触发依据**：主回答中的“连接打开并不代表此前的完成事件送达”

**口播版**：列表先返回运行中，消费者紧接着完成并发布，但服务端 Redis 订阅还没生效，通知就丢了。之后 SSE 正常打开，前端关闭轮询，页面可能一直停在运行中。当前没有历史回放和初始终态快照。现在回看，可在订阅确认后读取并发出当前状态，辅以低频对账和版本判断，避免快照与事件乱序。

**追问 2**：你说静默查询当前页，如果用户这时换搜索条件，会不会显示旧结果？

**触发依据**：主回答中的“静默查询当前页”，上一回答中的“版本判断”

**口播版**：当前可能。普通查询、SSE 与轮询都能发请求，旧查询慢返回后没有请求序号检查，会覆盖新搜索。useCallback 不负责结果顺序。我会按查询身份递增序号，只接受仍属于当前查询的响应，或取消旧请求并在更新处再次检查。事件顺序与查询响应顺序要分别处理。

**追问 3**：页面关闭或进入后台时，连接和定时器怎么清理？

**触发依据**：主回答中的“响应页面可见性事件”

**口播版**：EventSource 和建连定时器在 effect cleanup 中关闭，服务端请求取消后关闭订阅和心跳；终态也会主动关连接。轮询监听可见性变化，隐藏时清定时器，恢复时立即查询。但已经发出的请求没有取消，旧回调返回后也可能重新安排定时器，所以它还不是严格的后台零请求保证。

### Q5 图表契约与渲染容错

- 对应支柱：B5
- 触发依据：“Zod 检查图表结构”“回退配置”“React 错误边界”
- 考查目标：理解运行期校验、接受范围、安全过滤与异常边界
- 学习入口：[C07](../guide-fullstack/07-图表契约与容错.md)

**面试官问题**：模型返回的图表配置为什么需要多层处理？每层保护什么？

**口播版**：我把模型返回值当作运行期数据，TypeScript 类型不能保证它的内容。先用 JSON 解析，必要时尝试去掉外层杂文，再用 Zod 检查非空系列与支持的类型，接着过滤函数文本和部分敏感字段，最后交给 ECharts。解析或结构失败会显示原因并尝试 fallback；渲染阶段的 React 子树异常由错误边界展示失败与重试。这些层保护不同问题。当前 schema 比较宽松，失败时仍可能渲染过滤后的原对象，所以我会把能力称为校验与容错，不会说已经严格拒绝全部非法配置。

**追问 1**：你说过滤敏感字段，它能保证所有配置都安全吗？

**触发依据**：主回答中的“过滤函数文本和部分敏感字段”

**口播版**：不能。当前过滤依赖 key 与字符串特征，会误删正常文本，也没有严格限制所有对象值、链接资源、深度和数据规模。JSON.parse 本身不执行代码，但后续图表库仍有自己的接受范围。若要求更强安全，应缩小字段白名单、限制资源预算，校验失败只渲染固定空图，并在服务端落库前校验。

**追问 2**：你说有重试按钮，是不是点击就重新让 AI 生成？

**触发依据**：主回答中的“错误边界展示失败与重试”

**口播版**：不是当前行为。错误边界只重置自己的错误状态，可选调用上层回调；现有主要调用方没有传重试请求，所以会用原配置再渲染。边界也不会因输入改变自动清除错误。要真正重新生成，需要单独的业务接口和状态控制，不能把组件重试等同于任务重试。

### Q6 看板与数据预览

- 对应支柱：B6
- 触发依据：“图表 ID…栅格布局”“保存本地图表快照及布局”“可见范围渲染行”
- 考查目标：解释状态所有权、稳定身份、持久化范围与虚拟化成本
- 学习入口：[C08](../guide-fullstack/08-列表状态与数据预览.md)、[C09](../guide-fullstack/09-看板布局与持久化.md)

**面试官问题**：看板如何把多张图与布局对应起来？原始数据预览如何减少渲染负担？

**口播版**：我用图表 ID 连接业务对象、React key 和栅格 item key，添加时排除已存在 ID，拖拽和缩放只更新布局状态。点击保存把图表对象快照与布局写进 localStorage，刷新读取最近保存内容。原始 CSV 弹窗把行交给 react-window，只渲染视口附近的行，降低 DOM 创建规模。这里要区分两种边界：看板是当前浏览器的本地快照，没有跨设备同步或自动刷新业务内容；虚拟行减少渲染节点，但整段 CSV 仍要下载、解析并保存在内存中。

**追问 1**：你说本地快照，如果换账号或者原图被更新了，会发生什么？

**触发依据**：主回答中的“图表对象快照…localStorage”“没有…自动刷新业务内容”

**口播版**：当前存储 key 没有按用户区分，换账号仍可能读旧快照，原图更新也不会自动反映。现在回看，布局应作为用户偏好，业务数据按图表 ID 重取并鉴权；可以把本地 key 分用户并加 schema 版本，或者在后端保存布局。当前也只向栅格传回 lg 布局，不能声称所有断点都完整恢复。

**追问 2**：你说整段 CSV 都要解析，带引号和逗号的单元格能正确展示吗？

**触发依据**：主回答中的“整段 CSV…解析”

**口播版**：当前预览的简单 split 不能处理标准 CSV 的引号、嵌入换行与逗号字段。例如“华东,上海”应是一个字段，却会拆成两列。后端 xlsx 转 CSV 会正确转义，这反而暴露两端语义差异。应换符合 CSV 规范的解析器；更大文件可以改服务端分页预览，同时控制传输与内存。

### Q7 会话与权限

- 对应支柱：简介
- 触发依据：简介中的“用户上传”“异步任务进度展示”，需要识别用户与图表归属
- 考查目标：区分前端路由控制、后端鉴权与资源授权
- 学习入口：[C02](../guide-fullstack/02-会话与接口契约.md)

**面试官问题**：用户刷新后怎样恢复登录状态？怎样控制图表访问权限？

**口播版**：我在登录成功后把用户 ID 保存进 Redis 会话，浏览器用 Cookie 携带会话标识；刷新时前端调用登录用户接口恢复展示状态。后端 Auth 从会话读 ID，再查数据库并把用户放入请求上下文，管理员接口额外检查角色。个人列表强制使用当前用户条件，编辑删除检查归属，SSE 也只允许归属者订阅。前端菜单隐藏只是展示控制。当前普通图表读取和通用列表没有统一归属限制，所以不能把局部检查说成完整多租户隔离。

**追问 1**：你说 Cookie 会话，HttpOnly 就能解决账户安全吗？

**触发依据**：主回答中的“浏览器用 Cookie 携带会话标识”

**口播版**：不能。HttpOnly 主要减少脚本直接读 Cookie，当前还有 SameSite=Lax，但 Secure、CSRF、防暴力尝试与完整资源授权都需要另行设计。密码仍是固定盐 MD5，账号索引也不是唯一索引。生产使用应改密码专用哈希、唯一约束、TLS Cookie 与一致授权策略。

**追问 2**：如果后端用 HTTP 200 返回业务失败，前端怎样区分？

**触发依据**：主回答中的“前端调用登录用户接口恢复展示状态”

**口播版**：必须读业务 envelope。Go 返回 code/data/message，code 为零才是业务成功；当前前端残留的错误抛出器却读 success/errorCode/errorMessage，存在静态契约不一致。应先统一解析规则，再决定错误提示或登录跳转，并用成功、未登录和权限不足的真实响应验证，而不只看 TypeScript。

### Q8 验证与交付

- 对应支柱：简介
- 触发依据：简介中的“React/TypeScript 与 Go”“Redis 与 RabbitMQ”，意味着跨进程和两端协作
- 考查目标：识别测试覆盖与部署范围，准确表达工程证据
- 学习入口：[C10](../guide-fullstack/10-测试与交付边界.md)

**面试官问题**：你怎样判断这套全栈项目能工作，现有测试和部署配置证明了什么？

**口播版**：我按层次看证据。后端已有 CSV 和清洗逻辑测试、CAS 结果分类、fake outbox 扫描，以及 HTTP 模型取消测试；本次在 Go 1.27.1、macOS arm64 执行现有 go test，全部通过。前端类型检查也通过，工作流包含格式、lint、类型、可为空的 Jest 和构建。Compose 启动三个中间件，应用仍要分别启动 HTTP、消费者和前端。这些证明局部测试与配置存在，不能证明真实数据库事务、消息恢复、两端契约或线上性能都已验收；最需要补的是会违背受理、恢复和展示承诺的端到端边界。

**追问 1**：你说现有测试通过，为什么还需要验证重试和事务？

**触发依据**：主回答中的“CAS 结果分类、fake outbox”“不能证明真实数据库事务、消息恢复”

**口播版**：CAS 测试只检查零行和错误如何分类，没有真实执行并发 UPDATE；relay fake 不验证数据库回滚、broker 确认或进程崩溃。它们也没覆盖“首次已经运行中、第二次被跳过”的组合路径。应补真实依赖集成与状态机组合验证，测试的价值取决于覆盖的承诺，不取决于命令返回成功。

**追问 2**：你说 Compose 启动依赖，是否已经可以直接上线？

**触发依据**：主回答中的“Compose 启动三个中间件…应用仍要分别启动”

**口播版**：当前是开发环境配置。生产还需要静态资源与 API 的同源转发、TLS 与 Cookie、SSE 缓冲和空闲超时、数据库迁移、消费者存活与重连、应用停机等。现有工作流上传构建产物，不是部署；health 也不检查完整任务链。没有实际环境证据时，我不会把这些说成已经完成的上线工作。
